## 一、超时与服务容量类

> **这类问题的本质**：本地开发时数据量小，一切正常；一旦上真实数据（几百页 PDF），请求体暴涨，服务撑不住。

### 1.1 大批量 embedding 请求 HTTP 超时

| 维度 | 内容 |
|:--|:--|
| **现象** | 导入 307 页 PDF（1125 个切片）时，向量化阶段报 `requests.exceptions.ReadTimeout: Read timed out (read timeout=120)` |
| **报错位置** | `embedding.py` 的 `_encode_http` → `requests.post(..., timeout=120)` |
| **根因** | 1125 个文本**一次性** POST 给 embedding 服务，服务端要逐批做 bge-m3 前向推理，处理时间远超 120 秒 |
| **排查过程** | ① 看报错栈 → 定位到 HTTP 超时 ② 检查 embedding 服务日志 → 服务没崩，是处理太慢 ③ 算一下：1125 条 × bge-m3，单条约 0.1 秒 = 112 秒，接近超时边界，网络抖动就超 |
| **失败尝试** | ❌ 想过加大 timeout 到 600 秒——治标不治本，更大的文档还是会超 |
| **最终修复** | `_encode_http` 改为**分批发送**：每批 32 条，循环发送，最后合并结果 |
| **自测验证** | `curl -X POST /encode` 发 2 条 → 正常返回（验证服务本身没坏）|
| **真测验证** | 重新导入 1125 切片的 PDF → 成功（约 5 分钟，分 36 批完成）|

**关键代码改动**（`embedding.py`）：
```python
# 修复前：一次性发
def _encode_http(self, texts):
    resp = requests.post(url, json={"texts": texts}, timeout=120)  # 1125条 → 超时

# 修复后：分批发
def _encode_http(self, texts):
    BATCH = 32
    all_dense, all_sparse = [], []
    for i in range(0, len(texts), BATCH):
        batch = texts[i:i+BATCH]
        part = self._encode_http_batch(batch)
        all_dense.extend(part["dense_vecs"])
        all_sparse.extend(part["lexical_weights"])
    return {"dense_vecs": np.array(all_dense), "lexical_weights": all_sparse}
```

**教训**：涉及批量外部调用的接口，**永远要分批**。不能假设"测试时 10 条能跑，1000 条也能跑"。批大小的选择要权衡：太小→HTTP 开销大；太大→单批超时。32 是 bge-m3 在 M 系列芯片上的经验值。

**排查这类问题的通用方法**：
```
1. 看报错是 Timeout 还是 ConnectionError
   - Timeout → 服务在处理但太慢（分批/优化）
   - ConnectionError → 服务挂了（重启/查日志）
2. 算数据量：多少条 × 单条耗时 = 预期总耗时
3. 看 timeout 设置 vs 预期耗时
4. 如果是 GPU 推理，还要看显存是否够（OOM 会导致服务重启）
```

### 1.2 embedding 服务未启动（服务发现）

| 维度 | 内容 |
|:--|:--|
| **现象** | 跑导入脚本，报 `ConnectionRefusedError: Connection refused` 或 `embedding=None` |
| **根因** | embedding 服务是独立 HTTP 进程，没开机。Milvus/Redis/MinIO 在 Docker 里会自动起，但 embedding 服务是手动起的 |
| **排查** | `nc -z localhost 8002` → DOWN；查进程 `ps aux | grep embedding_server` → 无 |
| **修复** | 手动启动：`python -m agentforge.knowledge.embedding_server --model .../bge-m3 --port 8002` |
| **自测验证** | `curl http://localhost:8002/health` → 返回 `{"status":"ok"}` |
| **真测验证** | 导入脚本能正常向量化 |

**教训**：基础设施依赖检查要放在最前面。每次开始工作前先跑一遍健康检查：
```bash
nc -z localhost 19530  # Milvus
nc -z localhost 8002   # Embedding 服务（手动起的！）
nc -z localhost 6379   # Redis
nc -z localhost 9002   # MinIO
```

## 二、版本兼容类

> **这类问题的本质**：依赖库升级后 API 变了，你的代码还在用旧 API。这是 Python 生态最常见的坑。

### 2.1 transformers 5.x 移除 prepare_for_model 导致 reranker 崩溃

| 维度 | 内容 |
|:--|:--|
| **现象** | 调用 `/rerank` 端点返回 `Internal Server Error`；检索结果的 `rerank_score` 全是 0.000 |
| **报错** | `AttributeError: XLMRobertaTokenizer has no attribute 'prepare_for_model'` |
| **根因** | `transformers 5.14.1` 移除了 `prepare_for_model` 方法；FlagEmbedding 的 `FlagReranker` 内部调这个方法 |
| **排查过程** | ① 看服务日志 → 找到 AttributeError ② `grep -rn "prepare_for_model" FlagEmbedding/` → 发现 14 处调用 ③ 确认 transformers 版本 5.14.1 ④ 查 transformers changelog → 确认 5.x 移除了这个方法 |
| **失败尝试 A** | ❌ Monkey-patch 补回 `prepare_for_model`——测试发现 `build_inputs_with_special_tokens`、`truncate` 也被移除了，重建需要太多被删的内部方法，太脆弱 |
| **失败尝试 B** | ❌ 降级 transformers 到 4.x——影响面大，项目其他地方可能依赖 5.x 特性，连锁反应不可控 |
| **最终修复** | 换用 `sentence-transformers` 的 `CrossEncoder`——加载**同一个** bge-reranker 模型，行为等价，且兼容 transformers 5.x |
| **自测验证** | `CrossEncoder(path).predict([['q','d']])` → 返回分数，无报错 |
| **真测验证** | ① `curl /rerank` → 返回 `{"indices":[0,3,2],"scores":[0.73,0.50,0.50]}`（有区分度） ② 检索结果 `rerank_score` 从 0.000 变成 0.73 |

**关键决策点——为什么选 CrossEncoder 而不是降级**：

```
                    降级 transformers          Monkey-patch           换 CrossEncoder
                    ─────────────────          ────────────           ───────────────
影响范围             全局所有依赖                局部（只改一个方法）      局部（只改 reranker）
风险                高（可能破坏其他模块）        中（依赖太多被删方法）   低（成熟库，接口稳定）
工作量              小（pip install）           大（要重建多个方法）     小（改 3 行代码）
                    ─────────────────────────────────────────────────────────────
最终选择                                                                ✅
```

**教训**：
1. 遇到版本兼容问题，先 `grep` 看报错方法被调用了多少处——如果只有一两处，patch 可行；如果十几处（像这个），说明这个库整体没跟上新版，应该换库
2. 优先找**等价替代**而非降级——降级一个基础库（transformers）的影响面远大于换一个上层库（FlagReranker → CrossEncoder）
3. 模型权重和加载库是**解耦的**——bge-reranker 的 `.bin` 文件谁都能加载，FlagEmbedding 和 sentence-transformers 加载的是同一个权重

**排查版本兼容问题的通用方法**：
```bash
# 1. 确认版本
pip show transformers | grep Version

# 2. 看报错方法在依赖库里被调用多少处
grep -rn "报错方法名" .venv/lib/python*/site-packages/依赖库/

# 3. 看被删方法的替代方案
python -c "from 依赖库 import Tokenizer; print([m for m in dir(Tokenizer) if '类似功能' in m])"

# 4. 搜社区有没有人遇到同样问题
# GitHub Issues 搜 "方法名 + 库名 + 版本"
```

## 三、查询语法类

> **这类问题的本质**：数据库/向量库的查询 DSL 在不同版本间有差异，文档示例不一定对得上你装的版本。

### 3.1 Milvus JSON_CONTAINS 对字符串数组元素不生效

| 维度 | 内容 |
|:--|:--|
| **现象** | `filter_tags=["学习资料"]` 检索返回 0 条结果，但库里确实有这个 tag 的切片 |
| **根因** | 代码用的是 `JSON_CONTAINS(tags, '"学习资料"')`；Milvus 3.x 下这个函数对 JSON 数组里的**字符串元素**匹配不生效（对数字却生效——版本 bug 或设计如此） |
| **排查过程** | ① 先确认数据真的在：`client.query(filter='source=="..."', output_fields=['tags'])` → tags 确实是 `['AI Agent','学习资料',...]` ② 逐个测试不同过滤语法 |
| **测试过程** | 写了 4 种语法对比测试，结果：|
| | `JSON_CONTAINS(tags, "\"学习资料\"")` → **0 条**（不生效）|
| | `JSON_CONTAINS_ALL(tags, ["学习资料"])` → 3 条 ✅ |
| | `array_contains(tags, "学习资料")` → 3 条 ✅ |
| | `tags == ["学习资料"]` → 0 条（精确匹配，不对）|
| **最终修复** | 改用 `array_contains(tags, "学习资料")` |
| **真测验证** | `filter_tags=["学习资料"]` 从 0 条变成 3 条 |

**教训**：
1. **不要相信文档里的示例语法**——一定要用真实数据测一遍。很多文档示例是针对旧版本写的
2. 遇到"查不到但不报错"的情况，第一步是**确认数据真的在**（用最简单的条件查出来看），排除"查询语法问题"还是"数据没存进去"
3. 同一个语义有多种语法表达时（JSON_CONTAINS / array_contains / JSON_CONTAINS_ALL），**全部试一遍**，看哪个在你装的版本上生效

**排查"查不到数据"问题的通用流程**：
```
1. 数据真的在吗？  → 用最宽泛的条件查（filter='' 或 filter='source=="..."')
2. 字段值格式对吗？ → output_fields 看实际存储的值和格式
3. 语法对吗？      → 逐个测试不同写法
4. 索引建了吗？    → 看是否需要先 load_collection
5. 版本差异？      → 查官方文档对应版本的语法
```

## 四、数据质量类

> **这类问题的本质**：导入时没报错，检索时也没报错，但结果不对。这类问题最难发现——因为系统"看起来正常工作"。

### 4.1 扫描版 PDF 提取不出文字

| 维度 | 内容 |
|:--|:--|
| **现象** | 导入后切片数极少，或文本内容为空 |
| **根因** | PDF 分两种：文字版（文本层可直接提取）和扫描版（页面是图片，没有文本层）。pypdf 只能提取文本层，扫描版提取出空字符串 |
| **排查过程** | ① 导入前抽样检测：对每本书抽 3 页（前/中/后），看 `extract_text()` 返回多少字符 ② 发现 3 本书平均 0 字/页 → 扫描版 |
| **检测结果** | 深入理解 AI Agent: 685字/页 ✅ / 技术工程师24堂: 363字/页 ✅ / 像架构师一样思考: 546字/页 ✅ / Claude Code实战: 0字/页 ❌ / 从零构建代码智能体: 0字/页 ❌ / 工程智能系统: 0字/页 ❌ |
| **处理** | 只入库 3 本文字版；扫描版需要 OCR（pytesseract + tesseract-ocr-chi_sim），暂跳过 |
| **真测验证** | 导入后检查 `len(doc.text)`，少于 100 字符直接拒绝入库 |

**预防代码**（写进导入脚本）：
```python
if len(doc.text.strip()) < 100:
    print(f"❌ 文本极少，可能是扫描版 PDF")
    sys.exit(1)
```

**教训**：
1. **永远在导入前做数据质量检测**——不要假设输入数据是好的
2. PDF 处理的第一步永远是：**抽样看文本提取效果**，而不是直接全量处理
3. "没报错"不等于"没问题"——空文本也能切片（切成 0 个），也能入库（存 0 条），系统全程不报错

### 4.2 切片 section 字段为空

| 维度 | 内容 |
|:--|:--|
| **现象** | 导入后检索，所有切片的 `section` 字段是空字符串 |
| **根因** | `recursive` 切片策略只按段落/句子切，不保留当前所在章节标题；只有 `section` 策略才带标题 |
| **影响** | 无法按章节过滤检索；检索结果看不出内容属于哪一章 |
| **排查过程** | ① 查 Milvus 里存的 section → 全空 ② 看 chunker 代码 → `chunk_recursive` 里 `section=""` 写死 ③ 对比 `section` 策略 → 它保留了标题 |
| **修复** | 在 `chunk()` 主入口里加 `_locate_section`：切片完成后，用 chunk 首句去匹配 loader 已解析的 sections，回填所属章节 |
| **自测验证** | section 覆盖率从 0% → 95% |
| **真测验证** | 检索"多agent协作失败模式" → section 显示「10.5 多 Agent 协作的失败模式」✅ |

### 4.3 代码块内的 # 被误判为标题

| 维度 | 内容 |
|:--|:--|
| **现象** | section 回填后归属错误——chunk 被归到最后一个 section，而不是它实际所在的章节 |
| **根因** | loader 的 `_extract_md_sections` 用正则 `^#{1,3}\s+` 匹配标题，但没排除 ` ``` ` 代码块内的 `#`（如 Python 注释 `{role: "assistant"` 被当成标题）|
| **排查过程** | ① 打印 sections 列表 → 发现一堆垃圾标题（"第一次迭代 - LLM 看到上述轨迹..."）② 这些垃圾标题的 text 极短（3 字符甚至 0）③ 定位到 code block 内的 `#` 行 |
| **修复** | `_extract_md_sections` 加 `in_code_fence` 状态跟踪，遇到 ` ``` ` 切换状态，块内的 `#` 不当标题 |
| **真测验证** | sections 从 129 个（含垃圾）变成干净的章节结构；section 归属正确 |

**教训**：
1. 正则解析结构化文档（Markdown）时，**必须考虑代码块/引用块等上下文**——`#` 在正文里是标题，在代码块里是注释
2. 数据质量问题会**级联放大**——loader 解析错 → sections 有垃圾 → chunker 回填错 section → 检索结果误导用户
3. 发现"结果不对但没报错"时，**打印中间产物**（sections 列表、chunk metadata）是最高效的排查方式

## 五、配置类

> **这类问题的本质**：代码没 bug，但配置不对，导致功能根本没启用。这类问题最隐蔽——因为代码"运行正常"。

### 5.1 运行时配置缺少 infra 段

| 维度 | 内容 |
|:--|:--|
| **现象** | 调用 knowledge_search 工具报"知识库不可用（Milvus 未初始化）" |
| **根因** | 运行时配置文件 `~/.agentforge/agentforge_config.yaml` 里**没有 infra 段**，InfraManager 启动时跳过了知识库初始化 |
| **排查过程** | ① 确认 Milvus 服务在跑（`nc -z localhost 19530` → UP）② 看 InfraManager 代码 → `if milvus_config.get("enabled")` 为 False 就跳过 ③ 查配置文件 → 没有 milvus/embedding 配置段 |
| **修复** | 导入脚本里显式传 config（不依赖全局配置文件）|
| **教训** | 服务在跑 ≠ 功能启用。配置缺失时系统**静默降级**，不报错但功能不工作 |

### 5.2 model_path 为空时不创建 EmbeddingEngine

| 维度 | 内容 |
|:--|:--|
| **现象** | 调检索时报 `'NoneType' object has no attribute 'encode_query'` |
| **根因** | `knowledge/__init__.py` 的 init 逻辑：`if emb_config.get("model_path"):` —— 即使走 HTTP 模式（只需要 server_url），model_path 为空就不创建 EmbeddingEngine |
| **修复** | 传配置时 model_path 给个非空占位值（实际走 HTTP 不用它）|
| **教训** | 条件判断要考虑所有使用场景。HTTP 模式不需要 model_path，但代码却用 model_path 作为"是否初始化"的开关——逻辑不自洽 |

**排查配置问题的通用方法**：
```
1. 服务在跑吗？     → nc -z / curl health
2. 配置对吗？       → cat 配置文件 | grep 相关段
3. 配置被读取了吗？  → 加日志 print(config) 或看启动日志
4. 条件分支走对了吗？→ 看 if 判断逻辑，传入值是否满足条件
```

## 六、测试环境类

### 6.1 全量测试卡在 46%

| 维度 | 内容 |
|:--|:--|
| **现象** | `pytest tests/` 跑到 46% 就不动了，没有输出，不结束 |
| **根因** | 某些测试文件包含联网测试（调真实 LLM API），网络不通时无限等待 |
| **排查过程** | ① `ps aux | grep pytest` → 进程还在但 CPU 0%（说明在等 I/O）② 跳过可疑测试文件重跑 → 通过 |
| **处理** | 分离单元测试和集成测试；跑测试时排除联网测试 `--ignore=tests/test_agent.py` |

### 6.2 macOS 没有 timeout 命令

| 维度 | 内容 |
|:--|:--|
| **现象** | `timeout 90 pytest ...` → `command not found: timeout` |
| **根因** | `timeout` 是 GNU coreutils 命令，macOS 默认没有（需要 `brew install coreutils` 装成 `gtimeout`）|
| **处理** | 不依赖 timeout，改用 pytest 自带的 `--timeout` 插件，或直接 `--ignore` 跳过卡住的测试 |

**教训**：开发环境（macOS）和生产环境（Linux）的命令行工具集不同。脚本里不要用非标准命令。

## 七、验证方法论小结

### 7.1 两种验证方式的区别

| | 自测（开发者测试） | 真测（真实数据验证）|
|:--|:--|:--|
| **做什么** | 用小数据、mock 验证逻辑正确 | 用真实数据、真实服务跑完整流程 |
| **速度** | 快（秒级）| 慢（分钟到小时级）|
| **能发现** | 逻辑错误、语法错误、空指针 | 超时、容量问题、数据质量问题、版本兼容 |
| **不能发现** | 超时、数据质量、版本兼容 | — |
| **什么时候做** | 改完代码立刻做 | 关键功能上线前必须做 |
| **例子** | `curl /encode` 发 2 条文本 | 导入 307 页 PDF 看 1125 切片是否完整 |

### 7.2 这次开发中的验证对照表

| 功能点 | 自测 | 真测 | 结果 |
|:--|:--|:--|:--|
| embedding 服务 | `curl /health` + `curl /encode` 发 2 条 | 导入 1125 切片 PDF | ✅ |
| reranker | `curl /rerank` 发 4 条文档 | 检索结果 rerank_score 有区分度 | ✅ |

### 7.3 排查问题的通用心法

```
第一原则：先确认"现象是真的"
  ─ "查不到数据" → 先确认数据真的在（用最宽泛条件查）
  ─ "服务不可用" → 先 curl/nc 确认端口通不通
  ─ "功能没生效" → 先确认配置是否启用

第二原则：分治法缩小范围
  ─ 是代码问题还是数据问题？→ 换一份数据试试
  ─ 是本地问题还是服务问题？→ 直接 curl 绕过代码
  ─ 是配置问题还是逻辑问题？→ 加 print 看中间值

第三原则：打印中间产物
  ─ sections 列表、chunk metadata、配置 dict
  ─ 比看代码猜原因高效 10 倍

第四原则：全部试一遍
  ─ 同一语义的多种写法都试（JSON_CONTAINS / array_contains）
  ─ 同一功能的多个替代库都试（FlagReranker / CrossEncoder）
  ─ 别猜哪个能用，跑一遍最靠谱
```

## 附：问题分类速查

| 类别 | 特征 | 第一步排查 |
|:--|:--|:--|
| **超时/容量** | 报 Timeout、处理很慢 | 算数据量，看是否需要分批 |
| **版本兼容** | AttributeError、方法不存在 | `pip show` 查版本，`grep` 看调用处 |
| **查询语法** | 查不到数据但不报错 | 确认数据在，逐个测试语法 |
| **数据质量** | 结果不对但流程没报错 | 打印中间产物，抽样检查 |
| **配置** | 功能不工作、静默降级 | 查配置文件，看条件分支 |
| **测试环境** | 命令找不到、测试卡住 | 区分环境差异，跳过联网测试 |
