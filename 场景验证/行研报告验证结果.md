# 场景验证：行研报告写作 —— 验证结果

> **验证目的**：通过真实场景（写行研报告），端到端验证 AgentForge 系统的工程能力。
> 不是开发，是对 agent 系统的实战检验。
>
> **验证经历了四轮迭代**，每轮发现问题 → 修复 → 重新验证，最终验证了系统的上下文管理和长期记忆能力。

---

## 四轮验证总览

| 轮次 | 改动 | 最大上下文 | LLM 超时 | 工具调用 | 核心发现 |
|:--|:--|:--:|:--:|:--:|:--|
| **第一轮** | 无优化（基线） | 52,006 t (81%) | ❌ 崩溃 | 22 次 | 上下文爆炸：write_file 54KB + web_search 38KB |
| **第二轮** | +短期卸载 | 7,803 t (12%) | ✅ | 30 次 | 工具结果卸载生效，上下文降 85% |
| **第三轮** | +长期记忆 L0~L3 | 6,314 t (9%) | ✅ | 40 次 | recall_tool_result 被主动调 8 次，L1 自动提取 34 条事实 |
| **第四轮** | max_turns 50 + skill 优化 | — | ✅ | 55 次 | 发现 Milvus 长连接断开问题（真实工程问题） |

---

## 第一轮：发现问题（基线）

### 验证场景

| 维度 | 内容 |
|:--|:--|
| **场景** | 让 agent 写一份《企业级 AI Agent 系统架构设计》行研报告 |
| **Skill** | `research-report`（指导 agent 按步骤检索→搜索→画图→整合） |
| **工具组合** | knowledge_search + web_search + bash（画图）|
| **知识库** | kb_ai_implementation（1125 切片）+ kb_architecture（1997 切片）|

### 结果

agent 执行了 22 次工具调用，**生成了完整的 15KB 报告 + 3 张图表**。但在最后一步 LLM 流式响应超时（`httpx.ReadTimeout`），因为上下文涨到 52,006 tokens（81%）。

### 验证通过项

| 验证点 | 状态 | 证据 |
|:--|:--:|:--|
| Skill 自动触发 | ✅ | 第一个动作就是 read_file(SKILL.md) |
| 知识库检索 | ✅ | knowledge_search 5 次，两个 collection |
| 联网搜索 | ✅ | web_search 5 次（趋势/案例/市场/治理）|
| 代码画图 | ✅ | bash 8 次，生成 3 张 PNG |
| RAG 图片 | ✅ | 3 个 URL（huggingface/github）|
| 联网图片 | ✅ | 8 个参考链接 |
| 代码生成图 | ✅ | 3 张 matplotlib 图表 |
| 报告完整性 | ✅ | 15KB 报告（含摘要/5 章/参考来源）|

### 发现的问题：上下文爆炸

**根因分析（三个缺陷叠加）**：

```
1. 工具结果全量进上下文
   write_file 54KB → content 参数 54000 字进 tool_calls
   web_search 5次 × 7800字 = 39000 字工具结果
   knowledge_search 5次 × 5000字 = 25000 字工具结果

2. Headless 模式不触发压缩
   memory_monitor 只在 InteractiveSession 触发
   HeadlessRunner 不调 agent_context_compact

3. token 估算有盲区
   只算 m.content，不算 m.tool_calls.arguments
   压缩阈值 92% 太晚（81% 时 LLM 已超时）
```

## 第二轮：短期符号化记忆（上下文卸载）

### 改动

参照腾讯 TencentDB Agent Memory 的短期符号化记忆：工具结果卸载到磁盘，上下文只保留符号化摘要。

- 新建 `context/` 包（ToolResultStore + ContextManager）
- 新建 `recall_tool_result` 工具
- 改 agent.py：超长结果卸载 + 符号化回灌
- 压缩逻辑移入 agent 内核（所有模式都走）
- 压缩阈值 92% → 75%

### 结果

| 指标 | 第一轮 | 第二轮 | 变化 |
|:--|:--:|:--:|:--:|
| 最大上下文 | 52,006 t (81%) | 7,803 t (12%) | **-85%** |
| LLM 超时 | ❌ | ✅ | 修复 |
| 卸载数据 | — | 15 条，压缩率 93% | 节省 18,900 tokens |

---

## 第三轮：长期分层记忆（L0~L3）

### 改动

参照腾讯 L0~L3 四层金字塔：L3 核心画像 → L2 场景记忆 → L1 原子事实 → L0 原始会话。

- 新建 `memory/longterm.py`（LongTermMemory）
- 新建 `tools/longterm_memory_tool.py`（remember_fact / recall_memory / save_scenario）
- 会话开头自动注入 L3 画像 + L2 场景 + L1 事实
- 每 5 轮自动提取 L1 原子事实

### 结果

| 指标 | 第二轮 | 第三轮 | 变化 |
|:--|:--:|:--:|:--:|
| 最大上下文 | 7,803 t | 6,314 t (9%) | -19% |
| recall_tool_result | 0 次 | 8 次 | agent 学会按需调取 |
| recall_memory | 0 次 | 1 次 | agent 主动检索记忆 |
| L1 自动提取事实 | 0 条 | 34 条 | 长期记忆沉淀 |

**最有价值的发现**：agent 学会了符号化记忆的机制——需要原始数据时主动调 `recall_tool_result`（8 次），而不是让全量数据占着上下文。

## 第四轮：真实工程问题暴露

### 改动

- max_turns 30 → 50（复杂任务需要更多轮次）
- skill 优化：明确指定 .venv/bin/python（避免 agent 浪费轮次找 Python）

### 发现的工程问题

**Milvus 长连接断开**：

```
agent 前期 knowledge_search 正常（前 2 次成功，结果被卸载）
中期 Milvus 连接超时：Fail connecting to server on localhost:19530
后续 knowledge_search 全部失败 → agent 只能用 bash 手动 pdftotext + grep 读 PDF
```

这是 **Milvus 连接池的长时间空闲断开问题**——agent 跑了十几分钟后，Milvus 的 gRPC 连接被服务端断开。pymilvus 的连接恢复机制（`_recover`）没自动重连成功。

**影响**：不是记忆系统或上下文管理的问题，是基础设施层的连接稳定性问题。已记入后续待优化项。
